# 🌸 CycleCare - Menstrual Cycle Tracking Web Application

> **Educational Full-Stack Web Development Project**  
> *Demonstrating the fundamentals of Frontend, RESTful APIs, Backend Business Logic, and Relational Databases.*

---

## ⚠️ Important Educational & Medical Disclaimer

**CycleCare is built as an educational demonstration of full-stack web engineering concepts.**  
All upcoming period predictions and cycle lengths generated by this application are **transparent mathematical estimates** calculated strictly from past user-entered averages (e.g., `Last Period Date + Average Cycle Length`).  
- **CycleCare is NOT a medical device.**  
- **It does NOT provide clinical diagnosis, medical counsel, or contraceptive planning.**  
- Always consult a licensed healthcare professional for medical guidance regarding your menstrual cycle or reproductive health.

---

## 1. Project Overview & Goal

The goal of **CycleCare** is to allow a registered user to:
- **Create an account and authenticate securely** with encrypted password storage.
- **Log menstrual cycle details**: start dates, end dates, period durations, and cycle lengths.
- **View previous cycle logs** in an accessible, organized history table.
- **Update or correct** previous cycle records.
- **Delete** invalid or unwanted entries.
- **Receive transparent estimations** for their upcoming cycle date based on their historical logs.
- **Interact with a clean healthcare dashboard** presenting key wellness metrics without visual clutter.

## 3. Application Architecture & Communication Flow

CycleCare strictly adheres to a multi-tiered client-server architecture:

```text
       USER
         │
         ▼
 ┌───────────────┐
 │   Frontend    │  HTML5 + CSS3 + Vanilla JavaScript
 │   (Browser)   │  Client-side validation, form interception, modal UI
 └───────┬───────┘
         │
         │  HTTP Requests (JSON payloads via fetch API)
         ▼
 ┌───────────────┐
 │ Flask Backend │  RESTful Endpoints (/api/register, /api/cycles, etc.)
 │  (routes/*.py)│  Authentication, Authorization, Input sanitization,
 └───────┬───────┘  Cycle estimation business logic
         │
         │  Parameterized SQL Queries (%s placeholders)
         ▼
 ┌───────────────┐
 │ MySQL Database│  Relational Storage (users, cycles tables)
 │ (schema.sql)  │  Foreign keys, cascade on delete, indexes
 └───────────────┘
```

> **Key Rule**: The browser/frontend **never** speaks directly to MySQL. All database operations are mediated and validated by the Flask backend.

## 5. Database Design & Relational Schema

### Table: `users`
Stores user profile information and cryptographic password hashes.

| Field | Data Type | Constraints | Purpose |
| :--- | :--- | :--- | :--- |
| `id` | `INT` | `AUTO_INCREMENT`, `PRIMARY KEY` | Unique user identifier |
| `name` | `VARCHAR(100)` | `NOT NULL` | Display name of the user |
| `email` | `VARCHAR(150)` | `NOT NULL`, `UNIQUE` | Unique user login email |
| `password_hash` | `VARCHAR(255)` | `NOT NULL` | One-way salted password hash |
| `created_at` | `TIMESTAMP` | `DEFAULT CURRENT_TIMESTAMP` | Account registration timestamp |

### Table: `cycles`
Stores individual cycle logs linked to each user.

| Field | Data Type | Constraints | Purpose |
| :--- | :--- | :--- | :--- |
| `id` | `INT` | `AUTO_INCREMENT`, `PRIMARY KEY` | Unique cycle record ID |
| `user_id` | `INT` | `NOT NULL`, `FOREIGN KEY` | References `users(id)` ON DELETE CASCADE |
| `start_date` | `DATE` | `NOT NULL` | First day of menstrual bleeding |
| `end_date` | `DATE` | `NULL` | Final day of period bleeding |
| `period_duration`| `INT` | `NOT NULL` | Total bleeding days (e.g. 5 days) |
| `cycle_length` | `INT` | `NOT NULL` | Days from this start date to next (default 28) |
| `notes` | `TEXT` | `NULL` | Optional symptom/flow notes |
| `created_at` | `TIMESTAMP` | `DEFAULT CURRENT_TIMESTAMP` | Log creation timestamp |

## 6. REST API Endpoints

All API routes receive and return `application/json` responses.

| Method | Endpoint | Description | Status Codes | Auth Required |
| :--- | :--- | :--- | :--- | :---: |
| `POST` | `/api/register` | Create a new user account | `201`, `400` | No |

| `POST` | `/api/logout` | End session | `200` | Yes |
| `GET` | `/api/me` | Fetch active session profile | `200`, `401` | Yes |
| `GET` | `/api/dashboard` | Fetch summary statistics & estimate | `200`, `401` | Yes |
| `GET` | `/api/cycles` | Retrieve all cycles for logged-in user | `200`, `401` | Yes |
| `GET` | `/api/cycles/<id>`| Retrieve single cycle by ID | `200`, `401`, `403`, `404` | Yes |
| `POST` | `/api/cycles` | Create a new cycle record | `201`, `400`, `401` | Yes |
| `PUT` | `/api/cycles/<id>`| Update an existing cycle record | `200`, `400`, `401`, `403`, `404`| Yes |
| `DELETE`| `/api/cycles/<id>`| Delete an existing cycle record | `200`, `401`, `403`, `404` | Yes |

## 7. Cycle Estimation Mathematical Logic

The cycle estimation logic in CycleCare is deliberately simple, transparent, and grounded in basic statistics:

### Formula:
$$\text{Estimated Next Period} = \text{Latest Period Start Date} + \text{Average Cycle Length}$$

### Step-by-Step Calculation:
1. **Average Cycle Length Calculation**:  
   If a user has multiple cycle records (e.g., lengths of 28, 29, 27, and 28 days):
   $$\text{Average Cycle Length} = \frac{28 + 29 + 27 + 28}{4} = 28 \text{ days}$$
   *(If only one record exists or no previous length is calculated, the standard clinical benchmark of 28 days is utilized).*
2. **Upcoming Date Calculation**:  
   If the latest cycle start date is `October 1, 2026`:
   $$\text{Estimated Next Period} = \text{October 1, 2026} + 28 \text{ days} = \text{October 29, 2026}$$
3. **Countdown Presentation**:  
   $$\text{Days Remaining} = \text{Estimated Date} - \text{Today's Date}$$

## 8. Installation & Setup Guide

### Prerequisites
- Python 3.10+
- MySQL 8.0+ *(Optional: If MySQL is not running on your computer, CycleCare automatically falls back to local SQLite so you can test and grade immediately).*

### Step 1: Clone or Navigate to the Project
```bash
cd d:\cyclecare
```

### Step 2: Install Dependencies
```bash
pip install -r requirements.txt
```

### Step 3: Configure Database Credentials
Open `.env` in the project root:
```env
SECRET_KEY=cyclecare_secret_development_key
DB_HOST=localhost
DB_PORT=3306
DB_USER=root
DB_PASSWORD=your_mysql_password
DB_NAME=cyclecare_db
PORT=5000
DEBUG=True
```

### Step 4: Initialize MySQL Database (Optional)
If running MySQL, execute the schema:
```bash
mysql -u root -p < database/schema.sql
```
*(The Flask backend will also automatically create the database and tables upon server boot).*

### Step 5: Run the Application
```bash
python app.py
```
Open your browser and navigate to:  
👉 **`http://localhost:5000`**

### Step 6: Run Automated Tests
```bash
python test_app.py
```

## 9. Component Deep-Dive (Educational Explanations)

### Component 1: Frontend (HTML5, CSS3, Vanilla JavaScript)
1. **What it does**: Renders pages (`index.html`, `dashboard.html`, `history.html`), presents stats and tables, handles user input through forms, and triggers dynamic modals.
2. **Why it is needed**: Provides the human-facing interface so users can log cycles, see visual stats, and interact without touching database code.
3. **How it communicates with other components**: Uses browser `fetch()` API calls to send and receive JSON data over HTTP to Flask endpoints.
4. **What web-development concept it demonstrates**: **Client-side computing, semantic HTML, responsive CSS design, and asynchronous DOM manipulation**.

### Component 2: RESTful API & HTTP
1. **What it does**: Exposes structured URLs with standard HTTP verbs (`GET`, `POST`, `PUT`, `DELETE`) delivering JSON payloads.
2. **Why it is needed**: Decouples the user interface from backend business rules and database storage.
3. **How it communicates with other components**: Receives requests from JavaScript `fetch()`, hands data to Flask controllers, and returns HTTP status codes (`200 OK`, `201 Created`, `400 Bad Request`, `401 Unauthorized`).
4. **What web-development concept it demonstrates**: **Stateless client-server architecture and HTTP protocol standards**.

### Component 3: Flask Backend (Server-Side Python)
1. **What it does**: Directs web traffic via modular blueprints (`auth_bp`, `cycles_bp`, `dashboard_bp`), validates inputs, hashes passwords, and calculates cycle statistics.
2. **Why it is needed**: Secure computation and business logic must execute on a server where users cannot tamper with private credentials or access control rules.
3. **How it communicates with other components**: Receives HTTP requests from the browser, executes queries against MySQL via `db.py`, formats responses as JSON, and sends them back.
4. **What web-development concept it demonstrates**: **Server-side programming, separation of concerns (MVC/Blueprints), and session-based authentication**.

### Component 4: Relational Database (MySQL)
1. **What it does**: Persistently stores user accounts and cycle records across tables with foreign keys and indexes.
2. **Why it is needed**: Retains user data securely after the browser is closed or the server restarts.
3. **How it communicates with other components**: Receives parameterized SQL queries (`%s`) executed by the Flask backend database manager.
4. **What web-development concept it demonstrates**: **Relational schema design, referential integrity, indexing, and persistent storage**.

### Component 5: Authentication & Security
1. **What it does**: Hashes passwords using cryptographic PBKDF2/SHA-256 via Werkzeug, manages secure cookie sessions, and restricts cycle CRUD access (`WHERE user_id = session['user_id']`).
2. **Why it is needed**: Protects confidential personal health logs from unauthorized access and data breaches.
3. **How it communicates with other components**: The `@login_required` decorator checks `session['user_id']` before any route logic executes.
4. **What web-development concept it demonstrates**: **Authentication, Authorization, Data Isolation, and defense against SQL injection**.
